# Worked example: one R1 task and one R2 task, end to end

This is the filled-in version of the template's formats: a tracker issue,
a task contract (`templates/task-contract.md`), a worker handoff
(`templates/worker-handoff.md`), an independent-review verdict
(`.factory/skills/independent-review/SKILL.md`), and the post-merge
records. It follows one synthetic small project — a web dashboard everyone
calls **the console** — through two real-shaped tasks: an R1 refactor
(ENG-101) and an R2 change to verification logic (ENG-102).

Every ID, SHA, date, count, and command output below is synthetic and
self-consistent. Nothing here happened and no artifact below exists; the
point is that an adopter can copy each block and replace the synthetic
values with their own. The staging companion to the R2 task continues in
`examples/worked-host-validation.md`; an R3 authorization is traced in
`examples/worked-r3-example.md`.

## How the pieces fill each other in

- The **tracker issue** carries the acceptance evidence bar: what artifact
  proves the task, on which host (`docs/linear-workflow.md`). "Implement X"
  without a bar is not a ready task.
- The **task contract** is written before work starts and is the review
  anchor: acceptance evidence is judged against what the contract declared,
  not against what was convenient to produce.
- The **worker handoff** is written at a clean checkpoint; the worker then
  stops editing. The reviewer works from the handoff and the actual diff,
  never from the author's memory of them.
- **R2 changes** get the 7-condition independent review and merge only
  conditionally (`docs/risk-model.md`). R1 changes do not; they are
  autonomous with focused tests.
- After every merge: affected checks re-run at exact before/after SHAs,
  the issue closes with evidence pointers, the durable context gets one
  dated addendum line, and the daily report gets one line.

Timeline used below: ENG-101 runs 2026-06-02; ENG-102 runs 2026-06-03/04;
its staging companion (HVQ-07, ENG-103) runs 2026-06-04/05.

## Part 2 — R2: the deploy-readiness gate must verify observed state (ENG-102)

The console has a gate that reports whether a deploy succeeded. Its flaw
is the exact distinction this template exists to enforce: it treats a
successful deploy **request** (the API accepted it — an action) as a
**verified result** (the console is actually serving the new version). A
stuck rollout false-confirmed. Changing what "confirmed" means is R2.

### 1. The tracker issue

```text
ENG-102 — Deploy-readiness gate must verify the observed version, not
request acceptance
State: In Progress (LEASED — one writer on this surface)
Labels: R2, needs-machine

Body:
  The gate at src/deploy_check/gate.py reports status=CONFIRMED when the
  deploy API merely accepts the request (HTTP 200). Acceptance is an
  action, not a verified result: a stuck rollout false-confirms. Change the
  gate to re-fetch the served version after the request and report
  CONFIRMED only on an observed match; otherwise status=UNCONFIRMED,
  reason=observed_version_unchanged.

  ACCEPTANCE EVIDENCE (the bar):
  - at head on the dev host: gate unit suite passes, including the
    known-false-confirm case (stuck rollout) — the changed assertion must
    still catch it;
  - full suite before/after at base and head on the same host: same pass
    set, no regression (47 at base, 53 at head);
  - the changed assertion is justified in writing against the recorded
    incident, and the review re-derives the old gate's false-confirm at
    base;
  - the PR separates proven from unproven with host labels: the real
    staging observation is NOT part of this task's bar — it is ENG-103
    (HVQ-07), queued separately and never claimed here;
  - independent review: all 7 conditions verified and recorded before any
    conditional merge.
```

```text

    SHA) from unproven (real staging observation: UNEXECUTED_ON_STAGING,
    queued as HVQ-07 under ENG-103 — never claimed here);
(d) independent review verifies all 7 conditions and is recorded before
    any merge.

this task's merge bar and must not be claimed by it.

HUMAN / HOST TEST REQUIRED:
Yes — but for ENG-103, not for this task's bar: HVQ-07 (staging window,
TEST- operator sign-in, two prepared scratch builds). This task's merge
does not wait on it and does not claim it.

PRIVACY / DATA IMPACT:
None — the gate reads the internal deploy service's served version via a
read-only GET to the same service it already calls. No new logs, no new
egress path, no personal data.

EXTERNAL PROVIDERS / METERED?:
None — the deploy service is internal; tests stub it.

ROLLBACK POINT:
Revert the merge commit (main returns to the 2e8c45f tree). The frozen
provenance tag deploy-gate-pre-r2@2e8c45f preserves the old gate's
behavior for A/B re-derivation during review and any later rewrite.

TIME / ATTEMPT BUDGET:
One focused work cycle; at most 3 substantive attempts on the assertion
change, then a written root-cause analysis instead of thrashing.

STOP / ESCALATION CONDITIONS:
Making the new assertion hold requires weakening any other test; the
re-fetch cannot be done read-only; the diff grows beyond the two files; or
anything resembling a real deploy appears inside a test — that last one is
an unapproved R3 and a red line: stop, record, escalate.

SAFE PARALLEL WORK IF BLOCKED:
ENG-104 (saved-filters drawer UI, non-conflicting surface); ENG-106 (R0
runbook) if the review lane is busy.
```

### 7. What is deliberately still unproven

The merge did not make the gate "proven on staging." Three separate facts
stayed separate the whole way:

- **Attempt** — the console sent a deploy request (fixtures replay this).
- **Action** — the deploy API accepted it (the old gate stopped here and
  printed CONFIRMED).
- **Verified result** — the served version actually changed (only the new
  gate checks this, and only a real staging observation can certify the new
  gate doing so on the real pipeline).

That observation is `UNEXECUTED_ON_STAGING` — never pass, never fail, never
inferred from the dev host — and it continues end to end in

## The evidence phrasing this example models

- **PROVEN** is always "artifact at a stated SHA": "suite 47/47 at
  2e8c45f", never "tests pass".
- **UNPROVEN** is named before anyone has to ask: the R2 PR carries its
  own unproven section, with the host label attached
  (`UNEXECUTED_ON_STAGING`).
- **BLOCKED** is rare and always carries its unblocking condition; neither
  task above was ever blocked, and the Mission kept a non-conflicting
  surface (ENG-104) available throughout.
- **Attempt / action / verified result** are three facts, and the entire
  R2 bug was collapsing the second into the third.
- A truthful `UNCONFIRMED` (the new gate on a stuck rollout) beats a false
  `CONFIRMED` (the old gate) even though the old one looked greener.
- The daily-report and addendum lines cite their evidence the same way the
  closing comment does — a claim without a pointer does not appear.
